# Research: Application Icon

**Feature**: `024-client-app-icon` | **Date**: 2026-09-30 | **Plan**: [plan.md](plan.md)

## Decision: Which surfaces carry the identity, and how

**Rationale**: The client presents itself in four places, and three of them need work. Verified in the
current code: the project declares no application icon, the shell window declares no icon, and the shell
builds its own title bar (`ui:TitleBar` in `Views/MainWindow.xaml`) which — being a library control —
does not draw the operating system's title-bar icon at all. So the surfaces are:

| Surface | How it is reached |
|---------|-------------------|
| Application file in the file system, pinned taskbar entry | the executable's own icon resource |
| Taskbar button while running, Alt-Tab entry | the window's icon |
| The shell's custom title bar | the title bar control's icon element |
| Splash-less startup, forms, dialogs | inherit the window/executable icon; dialogs are owned windows and need nothing extra |

**Alternatives considered**: executable icon only — rejected, leaves the custom title bar with no
identity, which is the surface the signed-in user stares at; window icon only — rejected, leaves the file
system and the pinned entry with a placeholder, and the file is how the product is delivered.

## Decision: Asset format and frame set

**Rationale**: Windows asks for the same mark at several sizes and picks per context (16 in the title bar
and task list, 20/24 in some shell views, 32 in Alt-Tab and the small file listing, 48 in the medium
listing, 256 in tiles and previews). A single-size asset is upscaled by the shell and looks soft exactly
where it is seen most. The asset is therefore one multi-frame icon (`.ico`) carrying
**16 · 20 · 24 · 32 · 40 · 48 · 64 · 256** px frames, with the 256 px frame PNG-compressed and the smaller
frames uncompressed 32-bit with alpha, which every supported Windows shell reads correctly.

**Alternatives considered**: a single 256 px PNG referenced everywhere — rejected, shells then downscale
per context and the taskbar rendering suffers; separate loose PNG files per size — rejected, only the
`ico` container makes the shell pick the intended per-context frame, and loose files cannot serve the
executable icon.

## Decision: How the mark is produced and kept reproducible

**Rationale**: No artwork exists in the repository and no design tool or network access is available (the
feature must create the mark itself). The asset is therefore **generated by a committed script**
(`src/RAGGit.Client.WPF/Assets/generate-app-icon.ps1`) that draws the mark as vector paths and writes the
multi-frame `.ico`. Both the generator and the generated `.ico` are committed, so the shipped identity is
reviewable as a binary and reproducible as source; the geometry and the colour appear exactly once, in the
script, and the audit in [quickstart.md](quickstart.md) asserts the frames the asset claims.

**Alternatives considered**: hand-authoring the `.ico` with a drawing tool — rejected, nothing in the
repository or the toolchain can produce or review it, and it cannot be regenerated or re-coloured;
generating the asset during the build — rejected, the executable icon must exist when the compiler stamps
the executable, so it would add a pre-build target plus a design-time dependency for no gain; keeping only
the generator and no asset — rejected, the repository would not build the shipped identity without running
a script first.

## Decision: The mark — fixed brand colour and treatment

**Rationale**: FR-008 fixes the icon to one brand colour that does not follow the user's Windows accent,
and the client has no fixed colour anywhere today (every accent it shows resolves to the library's
theme-aware `SystemAccentColor*` tokens; the dashboard hero's gradient is built from the same tokens).
The feature therefore introduces the product's first fixed colour: **`#0F6CBD`**, the component library's
own brand-blue tone, so the identity matches the product's familiar appearance rather than inventing an
unrelated palette. The exact value is recorded once, with the asset, and the design-system reference gains
a line naming it so no later surface invents a second brand colour.

The colour is carried by the mark's **own filled tile**, not by a transparent silhouette: a rounded-square
tile in the brand colour holding a simplified product glyph in white. This is what makes a fixed colour
work on both light and dark shells — the contrast comes from inside the icon rather than from the shell —
and it keeps the identity readable when colour is ignored (the tile plus the glyph shape), satisfying the
"never identity by colour alone" rule the branding refresh established. The glyph is a simplified
document/library silhouette derived from the product's existing icon vocabulary, drawn bold enough to
survive 16 px, with a reduced small-size variant (fewer interior details) so the smallest frame does not
turn to mush.

**Alternatives considered**: the accent gradient already used by the dashboard hero — rejected by FR-008,
it varies with each user's Windows accent, so the shipped identity would not be fixed; a transparent
monochrome silhouette in the foreground colour — rejected, it reads as a system glyph rather than a
product identity and carries no brand colour at all; a letter monogram — rejected, the spec's assumption
keeps the mark text-free so it reads at taskbar size, and single letters are the weakest possible
distinguishing mark.

## Decision: Applying the identity to the shell

**Rationale**: Three edits, each verified against the library: the project file declares the asset as the
executable's icon and as a resource so the shell can reference it by pack URI; the window sets its icon
from the asset; and the shell's title bar receives an icon element through its nested `Icon` property —
the same trap the repository already documents for buttons, where the attribute form does not render.

**Alternatives considered**: replacing the title bar's product wordmark with the mark — rejected, the
wordmark is a deliberate treatment owned by `020`/`022`, and FR-001 asks for the icon alongside it, not
instead of it; relying on the window icon alone for the title bar — rejected, the library's custom title
bar never draws the operating system icon, so the surface would stay bare.

## Decision: How the identity is verified

**Rationale**: The evidence must be objective where the shell cannot be interrogated, and visual where it
can. The verifiable pieces are: the executable carries an icon and the asset carries the expected frame
set (both readable with a script); the brand colour is defined once (a text search); and the rendered
surfaces look right (screenshots). Two environments cannot be driven programmatically — the taskbar theme
follows the Windows app theme, and previews/tiles are shell behaviour — so light/dark legibility is proven
by compositing the asset's own frames over light and dark swatches and reviewing the result, plus the
standard screenshot pass with the capture pitfall in [quickstart.md](quickstart.md) accounted for.

**Alternatives considered**: adding unit tests — rejected for this project: the client has no unit-test
project, the asset is not library logic, and the server-side suites this repository runs are the wrong
home for it; relying on screenshots alone — rejected, a screenshot cannot show which frames the asset
actually contains, so a soft taskbar rendering would be undiagnosable.
